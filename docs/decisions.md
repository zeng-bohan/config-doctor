# 架构决策与贡献边界

2026-10-23 开始实现。项目由 AI Coding 辅助开发，代码的生成、测试通过和候选人已掌握是三种不同事实。面试前需要能够修改任务状态、审批和工具验证的核心源码。本文件不把生成代码记成既有个人工作经验。

## 为什么限制场景

自建结算服务提供超时、缓存价格、容量和税率四种配置异常。固定闭环使故障注入、恢复前后验证和安全边界可以独立复现；不能外推为复杂生产根因诊断。确定性程序也能分类这些异常，LLM 的作用是选择证据工具并生成解释，而非不可替代的数学分类能力。

## 为什么 Java 与 Python 分工

Java 的事务状态与权限是最终裁决者，Python 持有只读工具和提交提案能力。模型不调用审批接口，Java 不信任模型的根因、参数与证据引用。两进程增加了一次本机 HTTP 调用，但避免在 Java 内重复实现模型适配与评测脚本。数据量小，H2 文件持久化足够；没有引入 Redis、MQ 或向量库。

## 为什么不用框架隐藏循环

当前工具只有 probe、config、logs 与 submit_diagnosis。显式工具循环便于展示模型消息、错误返回、预算、中断恢复和最终校验。未来工具规模扩大后才能用实测复杂度决定是否引入框架，不能为关键词叠加多个框架。

## 为什么审批必须绑定版本

诊断证据对应某个配置版本。收集证据后如果配置改变，旧结论不再具有执行依据。Java 在审批事务中再次读版本，执行白名单补丁与复验，记录幂等结果。重复读取工具没有业务副作用，重复审批则由数据库唯一键和事务保护。

## 失败与观测

模型输出非法工具或参数时反馈结构化错误，不执行任意内容。模型超时、预算耗尽、Java 不可达时记录失败，不能返回伪造成功。messages 与证据由 Java 持久保存，Python 轨迹仅补充模型响应、用量与耗时。实验室未实现生产级追踪平台、租户隔离、SSO 或跨实例调度。
